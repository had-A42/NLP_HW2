## Что берём из семинаров

[Семинар 2](https://github.com/ashaba1in/hse-nlp/blob/a40420cc00bd27c4a45651bd650f495db077bb81/week02_transformer/seminar2.ipynb)
показывает encoder–decoder на `nn.Transformer`, обучение и beam search.
Клетка 56 полезна как учебный каркас, но её генерацию нужно адаптировать:

- Энкодер вызывается один раз, однако декодер пересчитывает весь префикс.
  Инкрементального KV-cache в этом примере нет.
- Цикл проходит все `max_length` шагов; нет корректного раннего завершения.
- В методе `generate` переменная `finished` используется через `+=` до
  инициализации. Это замечание по чтению кода, а не результат его запуска.
- Метрики и численные результаты перевода из семинара не оценивают pass@1 кода.

[Семинар 4](https://github.com/ashaba1in/hse-nlp/blob/a40420cc00bd27c4a45651bd650f495db077bb81/week04_modern_llms/seminar4.pdf):
страницы 8, 12–17, 19–31 посвящены расписанию LR, mixed precision, памяти,
activation checkpointing, attention и распределённому обучению. На странице 19
показана схема DDP: разные части данных, копии модели и синхронизация градиентов.
Для небольшой модели на двух T4 начинаем с DDP. FSDP, tensor/pipeline/context
parallelism оставляем за пределами первого решения; их необходимость должна
следовать из измерений памяти и скорости.

[Семинар 6](https://github.com/ashaba1in/hse-nlp/blob/a40420cc00bd27c4a45651bd650f495db077bb81/week06_speed_up/seminar6.ipynb):
клетки 23, 40–42 показывают ограничения наивных целочисленных операций и
CPU dynamic quantization. Клетка 52 описывает ускорение с BitsAndBytes для
DistilBERT в задаче классификации. Это не доказательство ускорения маленького
encoder–decoder при авторегрессионном декодировании на T4.

## Оговорки при переносе лекционных рецептов

1. Лекция 3, стр. 39, резко формулирует важность warmup. Лекция 4, стр. 47–48,
   различает Pre-LN/Post-LN и отмечает возможное ухудшение качества Pre-LN на
   небольших моделях. Наш выбор: warmup оставить в первом рабочем обучении,
   способ нормализации сравнивать отдельно.
2. Лекция 2, стр. 43, рекомендует beam search для seq2seq. Это не гарантия
   роста функциональной корректности программ; дополнительная стоимость
   особенно существенна при лимите 180 секунд.
3. Числа ускорения FlashAttention и RMSNorm из лекции 4 нельзя переносить на
   весь наш инференс. Нужны замеры полного пайплайна на T4. Сравнение на стр. 52
   относится к конкретной постановке и реализации нормализации.
4. Современная архитектура сама по себе не гарантирует улучшение маленькой
   модели с ограниченным временем обучения. Изменение FFN, нормализации,
   позиционных признаков и числа KV-голов проверяем по одному.
5. Варианты квантизации, включающие distillation loss, не подходят под запрет
   дополнительных таргетов. LoRA на внешней предобученной модели тоже не
   заменяет обучение нашего Transformer с нуля.

## Проверка совместимости с T4

- NVIDIA указывает T4 как GPU с compute capability 7.5:
  [таблица NVIDIA](https://developer.nvidia.com/cuda/gpus).
- Для первого запуска выбираем FP16 AMP с GradScaler. Не строим план на
  обязательной поддержке BF16 или TF32 на T4. Порядок autocast/scaler описан
  в [PyTorch AMP](https://docs.pytorch.org/docs/2.2/amp.html).
- Основная CUDA-реализация FlashAttention-2 рассчитана на Ampere/Ada/Hopper.
  Для Turing авторы отсылают к отдельной реализации с подмножеством функций:
  [официальный README](https://github.com/Dao-AILab/flash-attention#nvidia-cuda-support).
  Установку отдельного backend не включаем в обязательный путь до дедлайна.
- `scaled_dot_product_attention` может выбрать разные реализации. Наличие
  SDPA в коде не доказывает использование FlashAttention. Проверяем фактический
  backend и время: [PyTorch 2.2 SDPA](https://docs.pytorch.org/docs/2.2/generated/torch.nn.functional.scaled_dot_product_attention.html).
- В документации SDPA для 2.2 нет аргумента `enable_gqa`. GQA при этой версии
  требует отдельной реализации; материализация повторённых K/V может съесть
  ожидаемый выигрыш. Поэтому это поздняя гипотеза.

## Kaggle API и две GPU

По [официальной документации CLI](https://github.com/Kaggle/kaggle-cli/blob/main/docs/kernels.md)
и [метаданным kernel](https://github.com/Kaggle/kaggle-cli/blob/main/docs/kernels_metadata.md),
`NvidiaTeslaT4` соответствует GPU T4 ×2. Доступность и остаток квоты конкретного
аккаунта здесь не проверялись; реальный запуск ещё не выполнен.

План запуска, а не уже созданные удалённые сущности:

```bash
kaggle kernels push -p kaggle/train --accelerator NvidiaTeslaT4
kaggle kernels status OWNER/SLUG
kaggle kernels output OWNER/SLUG/VERSION -p artifacts/EXP-ID
```

Внутри kernel launcher запускает:

```bash
torchrun --standalone --nproc_per_node=2 train.py -cn=CONFIG_NAME
```

На этапе исследования поддержка DDP в нашем `train.py` отсутствовала.
В последующей реализации добавлена отдельная code-generation ветка; команды
и проверки находятся в [PIPELINE.md](../PIPELINE.md). При реализации учтены:

1. Один процесс на карту, `LOCAL_RANK`, CUDA device и process group с NCCL.
2. `DistributedSampler` либо согласованный sampler для батчей по длине;
   перемешивание по эпохам и одинаковое число шагов у обоих ranks.
3. Контроль эффективного батча: `2 * batch_per_gpu * accumulation_steps`.
4. AMP, корректный accumulation, `no_sync` на промежуточных микробатчах;
   clipping после unscale. LR меняется после шага оптимизатора.
5. При разном числе токенов у ranks не усреднять их средние loss без весов.
   Для сравнения и логов использовать общие суммы loss и непустых токенов.
6. Comet, сохранение файлов и checkpoints — на rank 0. Сохранять веса
   `model.module`, полный конфиг, токенизатор, состояния обучения и RNG.
7. По GPU отдельно логировать модель карты, память, загрузку и скорость.
   DDP держит копию модели на каждой карте; память не объединяется в одну.

Основание:
[PyTorch DDP](https://docs.pytorch.org/docs/2.2/generated/torch.nn.parallel.DistributedDataParallel.html).
Проверим ускорение 1 GPU → 2 GPU коротким замером. Если синхронизация съедает
выигрыш маленькой модели, альтернативой будут два независимых эксперимента
по одной карте, каждый с одним изменением относительно общего контроля.

Через Kernels API нужно отдельно обеспечить доступ к пакету `src`, конфигам,
токенизатору и данным. Не рассчитываем, что push одного `code_file` автоматически
перенесёт всё локальное дерево. План: приватные версионированные input-артефакты
и отдельный launcher; секреты через Kaggle Secrets. Версию kernel и каждого
input фиксируем в записи эксперимента. Публикации и запуски через API в рамках
этого исследования не выполнялись.

Окружение Kaggle фиксируем отдельно: версии PyTorch/CUDA, драйвер, GPU и
зависимости. Не переустанавливаем автоматически старые torch/torchvision из
общего шаблона поверх CUDA-окружения Kaggle. Возможности SDPA, компиляции и
GQA проверяем для фактически выбранной версии, а не смешиваем примеры разных
версий PyTorch.

## Дополнительные источники для дешёвых гипотез

[Attention Is All You Need](https://arxiv.org/pdf/1706.03762), разделы 3.4 и 6.1:
общая матрица embeddings/output projection и усреднение последних checkpoints.
Для нас это отдельные проверки: weight tying требует обучения новой модели;
checkpoint averaging совместимых весов даёт одну итоговую модель и не добавляет
второй forward на инференсе. Усредняем только совместимые floating-point веса
с одинаковыми архитектурой и токенизатором; качество не гарантировано.

[HF Cache strategies](https://huggingface.co/docs/transformers/kv_cache):
статические формы кэша могут облегчить компиляцию. Это источник идеи, а не
требование использовать библиотеку Transformers или готовую предобученную модель.
