# Идеи и гипотезы

Здесь хранятся потенциальные улучшения и результаты проверки гипотез.
Полные запуски и их численные результаты находятся в
[EXPERIMENTS.md](EXPERIMENTS.md). Идея становится проверенной только при наличии
описанной проверки и ссылки на её результаты.

Статусы: идея, подготовлена к проверке, проверяется, поддержана, не поддержана,
недостаточно данных. Один результат не доказывает универсальную применимость.

## Подтверждённые сведения

- [Датасет](https://huggingface.co/datasets/SlavaYus/tinysms_qa_12m):
  11 838 003 обучающих пары `question`/`code`, 1 919 тестовых условий без
  эталонных программ. Версия, прочитанная при исследовании:
  `b2724689ff079e9c22efd548fe134bfb29036dbb`.
- По [описанию](https://huggingface.co/datasets/SlavaYus/tinysms_qa_12m/blob/b2724689ff079e9c22efd548fe134bfb29036dbb/README.md),
  входная функция переименована в `solve`, docstring удалён. Программы перед
  публикацией не исполнялись; численных ответов нет. Один вопрос может иметь
  несколько программ.
- Задание требует encoder–decoder Transformer с обучением с нуля. Запрещены
  дополнительные обучающие данные и таргеты, включая дистилляцию.
- Весь тест нужно сгенерировать за 180 секунд на одной T4. Для 1 919 условий
  это средняя производительность около 10.7 задачи в секунду.

## Открытые вопросы

- Точный протокол проверки программ; формат посылки уже подтверждён
  пользователем: JSONL, единственное поле `code`, рекомендовано до 64 токенов.
- Какие операции входят в 180 секунд: загрузка, токенизация, генерация, запись.
- Фактическая доступность и остаток квоты Kaggle; целевой режим — две T4,
  до 4 часов на запуск.
- Способ локальной оценки функциональной корректности без дополнительных таргетов.
- Расхождение в конкурсных баллах: формула даёт 0.8 для последнего из 10
  участников, пример в задании указывает 0.5.

### Ограничение, определяющее порядок работы

Для 1 919 задач за 180 секунд нужна средняя скорость около 10.66 задачи/с.
При средней длине ответа L нижняя граница скорости выдачи токенов равна
`1919 * L / 180`, ещё без стоимости энкодера, загрузки и записи.

| Средняя длина ответа | Необходимая скорость токенов, не менее |
| --- | --- |
| 128 токенов | 1 365 токенов/с |
| 256 токенов | 2 730 токенов/с |
| 512 токенов | 5 459 токенов/с |

Это арифметика бюджета, не замер нашей модели. Рабочая цель — полный инференс
за 150–160 секунд, чтобы оставить запас до официальных 180 секунд. До
уточнения протокола отдельно измеряем холодный запуск до файла ответов и
генерацию после загрузки. Стоимость компиляции не считаем автоматически
исключённой из лимита.

### Что должно быть в первом рабочем бейзлайне

Это подготовка корректного и измеримого решения, а не список заявленных
улучшений качества.

- Обратимая токенизация Python-кода с сохранением отступов и переводов строк.
  Размер словаря и ограничения длин выбираем по статистике, не по названию модели.
- Компактный encoder–decoder со случайными весами, causal/padding masks,
  сдвигом labels, BOS/EOS и исключением PAD из loss.
- AdamW, warmup, clipping, FP16 AMP с GradScaler, корректные сохранение и resume.
- Заранее токенизированные данные и динамический padding. Они соответствуют
  H-001/H-003; их влияние на скорость измеряется техническими проверками.
- Переобучение на маленьком батче и проверка отсутствия утечки будущих токенов.
- Encoder вычисляется один раз; decoder self-attention KV-cache и кеширование
  encoder K/V для cross-attention. H-005 становится обязательной частью пути
  к быстрому инференсу, с проверкой против пересчёта полного префикса.
- Greedy decoding, остановка по EOS, предельная длина, сохранение всех row_id
  в исходном порядке, `eval()` и `inference_mode()`.
- Замер всего теста на одной T4 уже у первого обученного checkpoint.
  Не откладываем проверку лимита до конца обучения.

### Сначала проверки без нового обучения

Каждый вариант оцениваем на том же checkpoint, токенизаторе и списке задач.
Это отдельные технические проверки в EXPERIMENTS.md, а не полные EXP-запуски.

| Гипотеза | Проверка | Критерий и стоимость |
| --- | --- | --- |
| H-007: batch size и порядок входов влияют на полное время | Последовательно проверить 16/32/64/128, затем сортировку по длине условия; после сортировки восстановить row_id | Выбрать лучший размер без OOM по времени полного теста; проверять одни и те же условия. Низкая стоимость. |
| H-005: cache устраняет повторную работу | Сравнить cached и full-prefix logits в eval на коротких примерах; затем замерить генерацию | Согласованность выходов в пределах численной точности и фактическое ускорение. |
| H-006: предел генерации позволяет убрать избыточные шаги | Сравнить пределы, допустимые статистикой длин, и ранний EOS | Время, длины, доля без EOS и качество. Не сокращать ответы только ради таймера. |
| H-017: статический KV-cache и компиляция уменьшают накладные расходы | Сначала статическая предаллокация, затем отдельной проверкой `torch.compile` decoder-step | Полное холодное и прогретое время, число перекомпиляций, память. Отбросить при проигрыше холодного запуска. |
| H-011: усреднение последних checkpoints улучшает качество без удорожания модели | Сравнить лучший checkpoint с усреднением 3, затем 5 совместимых snapshots того же запуска | Одна итоговая модель; validation и генерация не ухудшаются. Усреднять floating-point веса в FP32, не optimizer/RNG. |

H-011 опирается также на раздел 6.1
[Attention Is All You Need](https://arxiv.org/pdf/1706.03762), где используется
checkpoint averaging. Перенос на нашу задачу — гипотеза.

Статическая предаллокация и компиляция — два изменения, проверяем их по
очереди. Аналогично размер батча и сортировку входов не меняем одновременно
при первом сравнении.

### Затем короткие обучающие абляции

Один полный запуск — один фактор. Начать с 2–3 наиболее дешёвых вариантов;
таблица ниже — каталог, а не обязательство запустить всё до дедлайна.

| Приоритет | Гипотеза | Единственное изменение | Что проверяем |
| --- | --- | --- | --- |
| P1 | H-010: скорость сходимости ограничена LR или warmup | Сначала LR; warmup менять только отдельным следующим запуском | Validation NLL и генерация за тот же бюджет токенов, NaN/overflow, нормы градиентов. Лекция 3, стр. 38–44. |
| P1 | H-002: меньше padding даёт больше полезных токенов за время | Случайные батчи → приближённая группировка по длинам question/code | Токенов/с, padding ratio и качество при одинаковом бюджете. Не включать глобальную сортировку без перемешивания. |
| P1 | H-008: более сильный encoder и менее глубокий decoder ускоряют ответ | Например, 4E/4D → 6E/2D при фиксированных ширине и tokenizer | Реальное число параметров, качество при сопоставимом времени обучения и инференс на T4. Сумма слоёв не означает одинаковое число параметров. |
| P1 | H-009: weight tying сокращает параметры с приемлемым качеством | Связать decoder embedding и output projection при общем словаре | Качество, число параметров, память и время; линейный выходной слой всё равно вычисляется. Основание: раздел 3.4 оригинального Transformer. |
| P2 | H-004: больший словарь сокращает число шагов генерации | Например, 8k → 16k, без изменения остальных гиперпараметров | Длины токенизации, полная скорость и качество; больший output projection может съесть выигрыш. |
| P2 | H-012: Pre-LN улучшает стабильность | Менять только положение LayerNorm | Сходимость и качество при фиксированных LR/warmup. Лекция 4, стр. 47–49 предупреждает о различии маленьких и глубоких моделей. |
| P2 | H-013: SwiGLU улучшает представления | Обычная FFN → SwiGLU с близким числом параметров FFN | Качество за GPU-время и скорость decoder-step. Для GLU ширину промежуточного слоя примерно уменьшить до 2/3 исходной, затем округлить и посчитать параметры. |
| P2 | H-014: RMSNorm уменьшает стоимость нормализации | LayerNorm → RMSNorm при том же положении нормализации | Качество и полное время, а не только время одного слоя. Лекция 4, стр. 50–52. |
| P3 | H-015: GQA уменьшает cache traffic | 4 query-heads / 4 KV-heads → 4 / 2 в decoder self-attention | Качество, память cache и время; не считать расширение K/V в обычный MHA бесплатным. Лекция 4, стр. 13–15. |
| P3 | H-016: RoPE улучшает моделирование позиций | Абсолютные позиции → RoPE только в self-attention | Качество и стоимость; cross-attention с двумя разными последовательностями не менять в той же абляции. Лекция 4, стр. 22–29. |
| P3 | H-018: точные дубли переусиливают часть примеров | Удалить только одинаковые пары question/code из исходного train | Доля дублей и качество при фиксированном бюджете; разные корректные программы одного вопроса не считать точными дублями. |

Для изменения LR и батчей удерживаем seed, данные и бюджет непустых токенов.
Для архитектур при ограниченном времени важен также срез при одинаковом
GPU-времени; фиксируем оба бюджета. При смене токенизатора обычные token-level
loss/perplexity несопоставимы: используем генерационную проверку и при
необходимости NLL на единицу исходного текста.

### Поздние методы и то, что не ставим в основной план

- H-019: INT8/weight-only quantization — только после FP16, cache и batching.
  Нужны реально быстрые T4 kernels, сравнение памяти, полного времени и
  качества. Уменьшение файла весов не доказывает ускорение генерации.
- H-020: beam=2 — только если greedy уже имеет большой запас времени и есть
  локальная оценка. Растут число декодируемых траекторий и cache; улучшение
  вероятности текста не гарантирует pass@1. Beam=5 не планируем первым.
- Speculative decoding из лекции 6 не запрещён сам по себе, если обе модели
  обучены только на разрешённых данных и исходных таргетах. Но обучение
  второй модели и сложная верификация не оправданы в первом варианте; не
  использовать дистилляцию draft-модели.
- Внешние предобученные модели, teacher-generated targets и дистилляция
  исключены требованиями HW2. Не включаем переписывание обучающих программ
  или генерацию новых решений в список обычных оптимизаций.
- MoE, tensor/pipeline parallelism, custom Turing kernels и activation
  checkpointing отложены. Последний имеет смысл при подтверждённой нехватке
  памяти и обычно покупает память дополнительным вычислением.

### Протокол обучения и оценки

1. Старое решение «пока без val» сохраняется для текущего датасета. Перед
   сравнением гипотез предлагается отдельный фиксированный holdout по
   уникальным вопросам; это ещё не реализовано. Например, 1–2 тысячи вопросов
   со всеми их вариантами code, исключёнными из train.
2. Не выдавать AST parse rate, наличие `solve`, token accuracy или NLL за
   функциональный pass@1. Численных эталонов в датасете нет. Возможность
   вычислять ответы reference только для локальной оценки требует уточнения
   протокола и ограничений задания; новых обучающих таргетов не создаём.
3. Для инференса отдельный процесс с `CUDA_VISIBLE_DEVICES=0`, без DDP.
   Логировать видимую GPU, dtype, tokenizer, checkpoint, batch size, предел
   длины, EOS/no-EOS, полные 1 919 выходов и сохранённый исходный порядок.
4. Синхронизировать CUDA на границах таймера. Отдельно записывать холодное
   end-to-end время и прогретое время генерации, включая декодирование в текст
   и запись в соответствующий полный замер. Сделать несколько повторов;
   решение с одним удачным временем около 180 секунд не считать надёжным.
5. Сохранять rank-0 checkpoint, tokenizer, resolved config, overrides, версии
   кода/данных/kernel и зависимости. Логировать полезные токены/с и фактически
   обработанные токены, не только число шагов.

### Порядок с учётом дедлайна

Срок решения по проверенному заданию — 24.10.2026 23:59, отчёта — 25.10.2026
23:59. На 23 октября полезнее ограничить число гипотез и сохранить рабочий
результат после каждого этапа.

1. Восстановить и запустить базовый пайплайн, проверить 2 GPU, измерить
   обучение и полный single-T4 inference. Провести короткий пилот для оценки
   времени большого запуска.
2. Не дожидаясь идеальной модели, сохранить воспроизводимую посылку и notebook.
3. Проверить H-007 и H-011 как дешёвые варианты без нового обучения.
4. Выбрать максимум несколько обучающих абляций: LR, затем группировка батчей
   или перераспределение encoder/decoder по наблюдаемому bottleneck.
5. Если уже есть запас времени и хороший результат, перейти к P2. Если нет —
   финализировать лучший checkpoint, воспроизводимость и отчёт.

По запросу пользователя от 2026-10-23 текущий бейзлайн увеличен с 11 632 640
до 31 647 744 параметров при словаре 8192: d_model=512, heads=8, FFN=1280,
encoder/decoder=4/4. Прирост — 20 015 104. Небольшой прежний вариант доступен
как `experiments=small_11m`. Это единый вариант масштаба архитектуры; вклад
изменения ширины отдельно от FFN здесь не изолирован. Статус: подготовлена к
проверке. CPU-корректность проверена; качество, память и полный инференс на T4
ещё нужно сравнить при исходном четырёхчасовом бюджете. Число слоёв декодера
не увеличивалось, но вычисления в каждом слое стали дороже.

### H-022: динамический бюджет padded-токенов

По решению пользователя от 2026-10-23 train и val переведены на бюджет
16 384 padded source+target токена на GPU. Число задач переменное;
max_batch_size=256, bucket_size=3200 на rank, accumulation_steps=2.
Локальная сортировка использует сумму исходных длин, затем строки
распределяются между ranks по очереди, а глобальные батчи перемешиваются.

Статус: реализация и CPU-корректность проверены. Результаты тестов и проверки
полного плана находятся в [журнале технических запусков](EXPERIMENTS.md).
Фиксированные 32 задачи с группировкой и без неё сохранены как контрольные
experiments=bucketed/fixed_batches. Измерение ускорения этой реализации и
влияния нового числа target-токенов на шаг на качество требует отдельного
запуска. Сравнивать качество следует при сопоставимом числе полезных
target-токенов и GPU-времени; одинаковое число optimizer steps недостаточно.

## Архитектуры и рост ёмкости — ресерч 2026-10-24

Запрос: изучить увеличение числа параметров, включая MoE, и выбрать
перспективные внедрения. Ниже — предложения для экспериментов. Новые
архитектуры не обучались; оценки качества и скорости для них не получены.
Рейтинг отражает ожидаемую пользу с учётом сложности внедрения в этот проект.

### Исходные условия и критерий отбора

- Текущая архитектура: d_model=512, heads=8, encoder/decoder=4/4,
  FFN=1280, ReLU, Post-LN, vocab=8192, пределы позиций 256.
  Это 31 647 744 параметра, включая общие encoder/decoder embeddings и
  отдельную выходную проекцию. Одна FFN содержит 1 312 512 параметров.
- Обучение с нуля либо преобразование только собственного checkpoint,
  обученного с нуля на разрешённых данных. Внешние веса, teacher outputs,
  новые обучающие примеры и дополнительные семантические таргеты исключены.
- До 4 часов на двух T4 за запуск; весь тест должен генерироваться за
  180 секунд на одной T4. Разреженная модель целиком должна помещаться
  на одну карту при инференсе, включая cache и временные tensors.
- Ранжируем по качеству за GPU-время, сложности реализации и риску.
  Число параметров, активные вычисления и фактическая скорость — разные
  величины. Большая модель при фиксированном времени увидит меньше данных.
  Такой компромисс подтверждается исследованием
  [Chinchilla](https://arxiv.org/abs/2203.15556), но его численные коэффициенты
  для decoder-only LM не переносим на нашу seq2seq-задачу.

### H-023: увеличение dense-модели

[Scale Efficiently](https://arxiv.org/abs/2109.10686) показывает, что форма
seq2seq-модели и режим compute влияют на downstream-результат: общего числа
параметров недостаточно. Более того, в исследованном авторами T5-режиме
они рекомендуют DeepNarrow: прежде увеличивать глубину. Поэтому место
dense-768 в нашем списке отражает простой и технически надёжный способ
удвоить ёмкость, а не универсальное преимущество ширины над глубиной. В работе
[Scaling Laws for Neural Machine Translation](https://arxiv.org/abs/2109.07740)
отдельно изучаются размеры encoder и decoder и расхождение между улучшением
cross-entropy и качества генерации. Эти результаты мотивируют сравнение
форм моделей, но не доказывают преимущество ширины 768 на нашей задаче.

Практический первый кандидат: умножить ширину d_model/FFN и число голов
на 1,5, сохранив 4E/4D, ReLU, Post-LN, tokenizer и данные. Это один
согласованный фактор масштаба: 64 773 120 параметров. Ширина 1024 при
heads=16, FFN=2560 дала бы 109 432 832 параметра. Последний вариант допускаем
только после короткого замера обучения: число обработанных target-токенов
за 4 часа может заметно уменьшиться.

### H-024: MoE только в encoder

[Switch Transformers](https://arxiv.org/abs/2101.03961) заменяет FFN набором
экспертов с выбором одного эксперта на токен. Авторы исследуют T5-подобную
encoder–decoder архитектуру и также показывают результаты с малым числом
экспертов в приложении D. Это непосредственно подходящий класс моделей.
Из статьи не следует такое же ускорение на T4 или в нашем небольшом режиме.

Наш первый вариант: неизменные attention/decoder, четыре encoder MoE-слоя,
E=4 или 8, k=1, каждый эксперт — прежняя ReLU FFN=1280. На токен приходится
одна FFN в каждом таком слое; разные токены одного вопроса могут задействовать
разных экспертов. Общие параметры и routing также требуют вычислений.
Утверждение о близком FFN compute не означает неизменное wall-clock время.

Encoder выбран потому, что он обрабатывается до авторегрессионного цикла.
В [ST-MoE](https://arxiv.org/abs/2202.08906), раздел 7, наблюдается различие
специализации encoder/decoder experts при span corruption. Это наблюдение
зависит от их objective и не гарантирует отдельного «эксперта по геометрии»
на supervised code generation.

План реализации, если этот вариант выбран:

1. Dropless token dispatch: вычислять только выбранных экспертов, затем
   объединять результаты. Padding исключать из routing и auxiliary losses.
2. Router logits/softmax и регуляризаторы считать в FP32 при остальном AMP
   FP16. Selective precision мотивирована Switch; перенос BF16-рецепта
   статьи на FP16 требует отдельной проверки численной устойчивости.
3. В top-1 сохранять обучаемый вес gate. Нормализация единственного
   выбранного веса до единицы уничтожает градиент router от основной задачи.
4. Стартовые коэффициенты: balance loss 0,01, router z-loss 0,001.
   Последний предложен ST-MoE; это отправная точка настройки. Оба члена
   используют состояния router, не внешние обучающие ответы. Их нормализацию
   по непустым source-токенам согласовать с accumulation и DDP.
5. Полный набор экспертов держать на каждой GPU, использовать data parallel.
   Expert parallel/all-to-all между двумя GPU на первом этапе не нужен.
   Для динамически неиспользуемых экспертов обработать unused parameters;
   это не устраняет стоимость синхронизации градиентов остальных параметров.
6. Логировать нагрузку и энтропию router, пустых экспертов, auxiliary losses,
   overflow, память и полезные токены/с. Проверять градиент router, DDP на
   пустых experts, causality и cache/full-prefix parity.

Проверка ускоряющих библиотек нужна отдельно: например, официальный
[MegaBlocks README](https://github.com/databricks/megablocks) рекомендует
grouped GEMM для Hopper. Сам факт наличия готовой библиотеки не подтверждает
её совместимость или выигрыш на T4; простая реализация для 4/8 экспертов —
кандидат для первого профиля, не заранее объявленная быстрая реализация.

#### Sparse upcycling как способ инициализации

[Sparse Upcycling](https://arxiv.org/abs/2212.05055) предлагает копировать
FFN обученной dense-модели в экспертов и инициализировать новый router.
Языковые эксперименты авторов используют T5; routing в encoder и decoder
у них различается. Это отдельная стратегия инициализации, совместимая
с H-024, но не подтверждение нашей конкретной top-1 конфигурации.

Для нас возможен warm start исключительно из собственного checkpoint,
полученного с нуля на разрешённых данных. Сравнивать его нужно с dense
continuation из того же checkpoint за то же дополнительное время. При
оценке суммарного compute учитывать и стоимость исходного dense-обучения.
Преобразование архитектуры требует отдельной загрузки весов и нового run;
существующий механизм exact resume для этого не подходит. Из-за множителя
gate даже одинаковые копии FFN не обещают побитового сохранения функции.

### H-025: SwiGLU и ширина FFN

[GLU Variants Improve Transformer](https://arxiv.org/abs/2002.05202) исследует
gated FFN в seq2seq T5 и сравнивает варианты при сопоставимом числе параметров
и вычислений. Для трёхматрицовой GLU hidden width уменьшается относительно
обычной FFN примерно до 2/3.

В нашем коде SwiGLU уже реализован. Важно: параметр `ffn_dim` автоматически
масштабируется и округляется до кратного 64. Поэтому при ffn_dim=3072
реальная SwiGLU width=2048, а размер модели — 46 350 336. Контроль:
ReLU, ffn_dim=3072, 46 342 144 параметра. Порядок проверки: сначала влияние
роста FFN на ReLU, затем SwiGLU при почти равном размере. Простая замена
activation при исходном ffn_dim=1280 даст width=896 и 32 176 128 параметров,
то есть сама по себе почти не увеличит общую ёмкость.

### H-026: более глубокий encoder

[Deep Encoder, Shallow Decoder](https://arxiv.org/abs/2006.10369) мотивирует
асимметричное распределение слоёв в задачах перевода. Его протокол содержит
дистилляцию, которую для HW2 не используем. Здесь заимствуем только идею
размещения ёмкости до авторегрессионной генерации; качество на коде неизвестно.

Чистая абляция: 4E/4D → 8E/4D при остальных исходных размерах, 41 108 480
параметров. Следующие ступени при той же ширине: 12E/4D — 50 569 216,
16E/4D — 60 029 952. Последний вариант полезен для сравнения с dense-768
при близком общем числе параметров, но другом распределении compute.
После проверки ширины 768 увеличение только encoder depth до 8
даёт 86 042 112. Стоимость encoder растёт; decoder self-attention/FFN и
размер его KV-cache при неизменной ширине не меняются. Подготовка K/V
cross-attention всё равно выполняется для каждого decoder-слоя.

[Pre-LN](https://arxiv.org/abs/2002.04745) — существующий переключатель для
отдельной проверки стабильности. [DeepNorm](https://arxiv.org/abs/2203.00555)
интересен при дальнейшем углублении; добавлять его в первый 8E/4D запуск
одновременно с несколькими другими изменениями не планируем.

### H-027: shared и более мелкие эксперты

[DeepSeekMoE](https://arxiv.org/abs/2401.06066) сочетает shared experts с
более мелкими routed experts, чтобы уменьшить дублирование общей информации.
[Scaling Laws for Fine-Grained MoE](https://arxiv.org/abs/2402.07871) отдельно
учитывает гранулярность и routing overhead. Это аргументы за дальнейший
эксперимент, а не доказательство ускорения маленьких experts на T4.

Наш пример shared-варианта: в каждом encoder-слое общая ReLU FFN=256 и
восемь routed ReLU FFN=1024, top-1. Суммарная активная hidden width=1280,
общее число параметров — 61 069 312. Это наша адаптация идеи, не точная
реплика DeepSeekMoE. Две активные FFN вместо одной дают больше вызовов kernels.
Увеличение количества маленьких experts/top-k рассматривать после замеров
простого H-024: стоимость routing и мелких matmul может перекрыть пользу.

### H-028: память как альтернативная ось роста

[Product-Key Memory](https://arxiv.org/abs/1907.05242) и
[Memory Layers at Scale](https://arxiv.org/abs/2412.09764) добавляют обучаемую
key-value память с разреженным доступом. Она хранит параметры модели,
не внешний набор документов. Во второй работе заметны gains на factual QA,
а также оцениваются code-задачи. Перенос на короткие математические задачи
и наш бюджет требует проверки.

Более свежий [Engram](https://arxiv.org/abs/2601.07372), версия v2 от июля
2026, использует hashed n-gram lookup и context-aware gating. Авторы сообщают
улучшения code/math и reasoning при сопоставимых параметрах/FLOPs в большом
режиме. Это даёт основание включить идею в список, но не переносить величину
прироста с их 27B-моделей на десятки миллионов параметров.

Минимальный вариант для нас — одна добавочная encoder-ветка памяти.
Только value table 65 536×512 содержит 33 554 432 параметра, вместе с базой
это уже 65 202 176 до query/key/gating-проекций. Нужно проверить обучаемость
редко используемых строк, работу Adam/AdamW с sparse/dense gradients,
стоимость DDP-синхронизации и memory bandwidth. В начале хранить таблицу
на GPU; перенос памяти на CPU и prefetch не входят в первый прототип.

### Что пока ниже в приоритете

- MoE в decoder и в attention: routing входит в каждый decoding step;
  требуется больше проверок устойчивости и cache parity.
- [Soft MoE](https://arxiv.org/abs/2308.00951): основная демонстрация в ViT;
  pooling по всем токенам нельзя напрямую переносить в causal decoder.
  Encoder-only вариант допустим как отдельная гипотеза.
- GQA, RoPE, RMSNorm: переключатели уже есть, но они сами по себе не решают
  запрос на большое увеличение числа параметров. Сокращение KV-heads уменьшает
  часть параметров; расширение контекста не является текущим условием задачи.
- Universal/looped Transformer увеличивает вычислительную глубину при общих
  весах, но не обеспечивает желаемый рост числа уникальных параметров.
- Сжатие, внешние pretrained модели, дистилляция и создание новых решений
  для обучения не входят в этот план.

### Подсчёты и минимальный протокол проверки

Dense-числа выше проверены созданием текущего CodeTransformer на meta device
и суммированием `p.numel()`, без forward, обучения и выделения больших весов.
MoE-числа рассчитаны для прежних ReLU-экспертов с bias и router Linear без bias:
`P_MoE = P_base + L * ((E - 1) * P_FFN + d_model * E)`.

| MoE-слои | Experts | Все параметры | Условный путь: все shared веса + один expert на MoE-слой |
| --- | --- | --- | --- |
| 2 encoder | 8 | 50 031 104 | 31 655 936 |
| 4 encoder | 4 | 47 406 080 | 31 655 936 |
| 4 encoder | 8 | 68 414 464 | 31 664 128 |
| 4 encoder + 4 decoder | 8 | 105 181 184 | 31 680 512 |

Последняя колонка — учёт параметров на условном маршруте, включая все shared
таблицы/проекции. Это не число выполненных FLOPs и не модель decoder-token
latency: encoder обрабатывает много source-токенов один раз и может задействовать
все experts для одного вопроса.

Порядок: короткий профиль dense-768 и простого encoder MoE, затем по результатам
выбрать полный запуск; SwiGLU и encoder depth держать отдельными абляциями.
Для MoE допустим отдельный upcycling pilot при сохранении dense continuation
как контроля. Исследовательскую память оставить после этих вариантов.

1. Технический профиль 500–1000 обновлений: useful target tokens/s, peak
   memory, padding, overflow, время загрузки и создания плана. Для MoE также
   imbalance, router losses и количество активных experts.
2. Сравнение при одинаковом wall-clock бюджете и отдельный срез по числу
   обработанных target-токенов. Не обещать всем архитектурам одинаковое
   количество шагов за 4 часа и не оставлять старый scheduler при смене плана.
3. Фиксированный validation по question, одна генерация на задачу и
   функциональная проверка. NLL и syntax rate — диагностические метрики.
4. Полный тест 1919 задач на одной видимой T4, свежий процесс, одинаковый
   decoding и токенизатор; минимум два повтора, запас относительно 180 секунд.
5. Приобретение ёмкости подтверждается только улучшением качества за выбранный
   бюджет. Увеличение файла checkpoint само по себе не является успехом.

## Boundary operators и рост глубины — 2026-10-24

Источник: [Chen et al., 2026, arXiv v2](https://arxiv.org/abs/2609.19107v2),
[код авторов](https://github.com/qlabs-eng/scaling-exponents).
Статья даёт основания разделить три новые гипотезы. Ниже — наш план адаптации;
прирост качества на HW2 и скорость этих вариантов не измерены.

### H-029: boundary operator в encoder

Предлагаемый оператор: `RMSNorm(h) + alpha * e`, где e — выход начального
encoder-блока. Это кандидат для проверки при неизменных размерах модели.
Первый прототип: encoder из prelude/core/coda с разбиением 1/2/1;
boundary map перед core и перед coda; сначала один проход core.
Decoder и формат данных сохраняются.

Наш исходный Transformer использует Post-LN. Для интерпретируемого опыта
нужен отдельный Pre-LN контроль той же формы, затем его вариант с оператором.
При четырёх encoder-слоях эффект может быть небольшим: польза для более
глубоких моделей ещё не означает пользу для нашего короткого encoder.
Alpha и LR проверять небольшим заранее заданным sweep, не считать одну
неудачную комбинацию опровержением идеи.

### H-030: повторение encoder core с общими весами

После H-029 сравнить один и два прохода одного core. При разбиении 1/2/1
два прохода исполняют шесть encoder-блоков при четырёх хранимых блоках.
Цель — проверить дополнительную вычислительную глубину, а не увеличение
числа уникальных параметров. Нужен контроль из шести независимых блоков
с тем же boundary operator и сопоставимым compute.

Encoder выбран для первого опыта, чтобы повторные проходы выполнялись до
генерации. Повторение decoder потребовало бы отдельного KV-состояния для
каждого прохода, даже при общих весах, и новых cache parity/causality тестов.
Дополнительные циклы не считать бесплатными по времени и не включать
произвольный новый loop count только при инференсе старого checkpoint.

### H-031: прогрессивный рост с независимыми копиями core

Ветка для роста уникальных параметров: активировать дополнительные копии
encoder core внутри одного запуска. Сравнивать с финальной большой моделью,
активной с начала обучения, за одинаковое GPU-время. Growth timing — отдельный
гиперпараметр; подбирать его на небольшом опыте и сохранять в checkpoint.

Нужны предсозданные модули или явная перестройка DDP, корректная работа с
неактивными параметрами, состояниями optimizer, LR в момент перехода и resume.
Копирование собственных обученных весов не требует внешних данных или
teacher targets. Такой запуск отличается от обычного exact resume и
не гарантирует сохранение функции модели в момент добавления слоя.

По цене внедрения H-029 стоит проверить раньше нового MoE-модуля.
H-031 остаётся более сложной веткой; H-030 оценивает compute, а не число весов.
В контрольной серии сохранять данные, tokenizer, decoding и бюджет времени;
оценивать функциональные решения и полный single-T4 inference.

### H-033: relative position bias в self-attention

Основание: [T5, раздел 2.1](https://www.jmlr.org/papers/volume21/20-074/20-074.pdf)
и [CodeT5-small config](https://huggingface.co/Salesforce/codet5-small/blob/main/config.json).
В self-attention добавляется обучаемое смещение по расстоянию query/key,
с отдельными значениями на голову. Близкие расстояния различаются точно,
далёкие объединяются в логарифмические buckets. В конфиге 32 buckets;
в T5 параметры bias разделяются слоями одного стека. Cross-attention
в исходной реализации не получает такое относительное смещение.

Наша гипотеза: относительные расстояния помогут моделировать структуру
условия и программы при изменении их длины. Улучшение математического
понимания или pass@1 из статьи для нашего режима не следует.

Для чистого опыта заменить learned absolute positions на relative bias,
оставив attention scaling, инициализацию, нормализацию, ReLU и размеры
контрольной модели. Это T5-inspired абляция, не точная копия T5.
Bias для cached decode должен учитывать реальную позицию query; будущие
и padded ключи остаются закрыты. Нужны full-prefix/cache parity, causality,
padding и повторные проходы layer_repeats. При float bias следует проверить
фактически выбранный SDPA backend и время полного single-T4 inference:
малое число параметров не гарантирует отсутствие замедления kernel.

Не переносим автоматически рецепт крупных CodeT5+: он использует shallow
encoder, deep decoder и frozen pretrained CodeGen. Источник —
[раздел 3.3 CodeT5+](https://arxiv.org/html/2305.07922v2).
При обучении с нуля замораживать случайный decoder не имеет этого обоснования;
более глубокий decoder увеличивает стоимость каждого output token.

План: проверять изменения последовательно на исходной модели с
layer_repeats=1. Текущий запущенный layer_repeats=3 остаётся отдельной
абляцией. Дополнительные targets, tokenizer или данные в эту серию не входят.
Состояние: исследование и подсчёт параметров; новых модулей/обучений нет.

## H-035: расширение beam при ограничении 180 секунд — 2026-10-24

Пользователь попросил расширить beam search на тех же обученных весах
и сообщил public pass@1: greedy=71,88%, beam=2 — 72,60%, beam=4 — 73,54%.
Это результаты со слов пользователя, бот ассистентом не вызывался.
Наблюдение поддерживает проверку более широкого beam на этой модели;
монотонного улучшения при любом дальнейшем расширении оно не гарантирует.

Критерий допуска: полный исходный test из 1919 задач, одна видимая T4,
два свежих Python-процесса на вариант, каждый <=180 секунд по внешнему
wall time. Pass@1 нового варианта определяется отдельно ботом; syntax parse
rate и вероятность последовательности не заменяют функциональную оценку.

- Сохраняются max_new_tokens=128, alpha=0.6, AMP FP16, static KV-cache,
  сортировка по длине и восстановление исходного порядка, tokenizer/model.
- [План](src/configs/inference_sweeps/beam_wide.json): beam=8/16 с batch=64/128,
  beam=24/32 с batch=64. Beam=48/64 допускаются условно только при запасе
  времени предыдущей ширины. Отдельно добавлены beam=12, batch=64/128.
- Модель берётся из уже экспортированного inference artifact. SHA256:
  13e84e4951ee823bf5d03ca2f7e5eb1078dc7e0d040cdba97eb7e144b837b80c.
  Копия на SSD проверяется по этому хешу; код исходного inference bundle
  проверяется по его manifest. Изменений весов и нового обучения нет.
- Batch size подбирается для времени/памяти; FP16 может давать разные
  predictions при разном batch, поэтому файлы и хеши сохраняются отдельно.
- [Launcher](kaggle/beam_sweep_launcher.py) выполняет адаптивный перебор;
  после первого timeout/OOM/превышения 180 секунд повтор этого варианта
  не нужен для признания его неподходящим. Успешный вариант обязан иметь
  оба полных замера. [Watcher](kaggle/watch_inference.py) скачивает только
  небольшие ответы и отчёты, затем проверяет формат и GPU-протокол.
- Запуски: andrewkhoroshilov/nlp-hw2-pre768-beam-sweep/1 и
  andrewkhoroshilov/nlp-hw2-pre768-beam12/1. Актуальные immutable планы:

  [промежуточный](kaggle/build/beam12/requested-plan.json).
